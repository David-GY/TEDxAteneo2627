# In-app notifications and delivery jobs

P30 uses the existing transactional outbox. Business commands commit their state, redacted audit and event together; no dispatcher runs inside that transaction. Delivery failure cannot undo a task transition, agreement, handoff, review or acceptance. No external adapter, provider configuration, secret or schedule is installed.

## Opaque delivery and current authorization

notifications stores only job/recipient/typed-target references, creation/read times and version. It stores no title, amount, body, recipient contact or copied authorization. Raw notification/preference/outbox access is denied, with forced RLS on the new tables. The service-only dispatcher selects current active core participants from actual assignments, scoped agreement heads/contribution ownership, handoff sender/receiver, requester/current reviewers/receiving heads, explicit mentions and pinned deliverable acceptance authority. Opaque candidate delivery is not a grant and is never exposed directly.

read_notifications resolves each row under the actual signed-in caller's existing source scope before pagination, count, unread badge, generic text or link. It uses actual work detail, agreement, handoff and request/workflow predicates; FIN/MCD actions use their typed guards. A contribution assignee without head scope gets only their independently permitted contribution task link. Requests never expose title/amount/package in an alert. No JWT claims are rewritten or recipient impersonation used by the worker. Current inactive/revoked membership denies inbox reads; lost source authority removes affected rows/counts. Destination routes independently check access again.

Action status comes from current records. A past decision/accepted handoff becomes a resolved update, rather than a stale approval button. Required work remains visible in its canonical pages regardless of delivery/preferences. Browser state is identity-bound, refreshes on navigation/focus/visibility and every20seconds while visible, hides old rows while rechecking or on error, and contains only generic alerts. This is not instantaneous push revocation proof; the server always checks current scope on a read or mutation, and links confer no access.

## Events, preferences and reminders

Fixed selectors cover task creation/assignment/progress, proposed/countered/accepted agreements, contribution assignment, proposed/responded/accepted handoffs, request submission/revision/assignment/decision and typed FIN/MCD changes, deliverable submission/acceptance/reopening/protected scope changes, and published current mentions. Unsupported outbox types are acknowledged without creating irrelevant chatter. Late dispatch resolves current participants and current action state; historical routing is not reconstructed from private payloads.

The service-only enqueue_notification_reminders adds bounded fixed in-app reminders two days before, on the due day, and daily overdue using Manila dates. Unique work/deadline/day keys make repeated enqueue idempotent. Deadline changes hide old reminder references. Terminal/archived work is excluded from new reminders. This is a fixed skeleton, not P41 configurable rules, a holiday calendar or an externally scheduled digest. Optional immediate/digest/mute preference is versioned and persisted; it does not suppress mandatory in-app rows. External quiet period20:00–08:00 Manila and actual digest transport remain inactive with external adapters disabled. Guest-only notification generation is not enabled by the core selector; no guest access is expanded.

## Worker, retries and custody

claim_notification_jobs is service-role-only, claims at most20 due/expired-lease jobs using row locks/SKIP LOCKED, increments attempts and gives an unpredictable60second lease. Expired fifth-attempt leases become failed. deliver_notification_job requires the exact live lease. It atomically inserts unique(job_id,recipient_id) references and acknowledges the job; failure rolls back inserted rows and persists only dispatch_failed, with30/60/120/240second backoff before the fifth-attempt failed state (bounded maximum3600seconds). A crash before commit leaves the lease recoverable; a lost response after commit cannot duplicate delivery. Failed business events remain in custody.

The Edge dispatch-notifications handler requires a server-only NOTIFICATION_DISPATCH_SECRET in x-notification-dispatch-secret; keep Supabase's existing gateway JWT verification enabled and invoke with an approved server JWT as well. It has no browser CORS allowance, accepts only an empty POST, compares the dedicated secret, enqueues at most100 reminders, claims20 jobs and processes at most4 concurrently. Server REST calls use a5second timeout and server-only service key. Responses contain counters/generic codes only; raw exceptions, payloads, IDs and secrets are not logged or returned. Failed/unknown HTTP completion leaves a committed lease for recovery. Local handler tests do not verify the real gateway/runtime.

read_notification_failures maps custody to explicit current term admin.configure authority; no head/PM label substitute. It exposes only the first50 attempted pending/claimed/failed queue records: opaque job ID, version, attempt count, safe code and next time. No source title, recipient list, payload or private error. retry_notification_job requires that scope, exact queue version, reason and idempotency key; it audits a redacted retry and starts a new bounded attempt cycle. No real custody role is seeded; institutional mapping and least-privilege activation remain open inputs.

Read/unread, preference and custody retry mutations use exact actor/command/key receipts and expected versions. Current permission is checked before replay. UI conflicts preserve safe fields; uncertain/malformed success freezes and retries the identical command/key without optimistic success.
