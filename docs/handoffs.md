# Immutable handoff domain (P17)

Migration022 adds handoffs, immutable handoff_revisions/handoff_decisions/handoff_receipts. Catalog48tables/546columns/67public functions. Forced RLS precedes exposure; no raw table grants/client writes. Handoffs are packages over existing canonical tasks, not another work/assignment model. P18 owns handoff screens.

submit_handoff(source task, exact receiver/unit, finalized manifest, terms, optional agreed next task, expected source/next versions, key, optional existing handoff/expected version) requires the current active source owner and independently permitted next task. Source must be Done under its existing completion rules. Terms are closed output/criteria/date-only dueOn/reason. The manifest must contain actual finalized uploads originating at that source, never a mutable working link or transitive financial attachment. Snapshot copies exact manifest/hash, sanitized file hashes/names/sizes/MIME, criteria, deadline, receiver and next task terms/versions. The original manifest retains its captured source version; editing a working source cannot change an offer.

With a next task, it must already be assigned to that receiver/unit, To do, same-term and connected by a required live P16 finish-to-start edge. P10/P14 owns prior assignment/negotiation authority. No new task is created. Without a next task, the exact receiving member must be a current deployed scoped committee head; acceptance records a package-only receipt. The first bounded model has one incoming handoff per canonical next task. Resubmission follows changes_requested/declined/cancelled, creates a new immutable revision and binds the current exact recipient/assignment. Accepted headers/receipts cannot be rewritten.

respond_to_handoff binds expected handoff version/revision and reason; exact receiver may accept, decline or request changes; current sender may cancel a proposed offer. accept_handoff is an explicit acceptance command with notes. Current membership/deployment/receiver assignment, original source/next versions and package state are checked again, including cached receipt/download authorization. P16 term graph locking precedes task/header/idempotency locks. Cancel-first and accept-first outcomes serialize; actual parallel provider verification remains external.

Acceptance atomically records accepted state, immutable exact-revision/manifest/criteria receipt, scoped read participation grants on the existing next task and activation through the ordinary authorized transition_task command. This preserves task completion/dependency rules, original deadlines, deliverable owner and FIN/MCD/acceptance gates. Decline/changes/cancellation cannot activate work; a pending/nonaccepted incoming handoff blocks task progress until explicit acceptance. Exact retries return one receipt and one activation. Immutable decisions and redacted audit/outbox references record every transition; no external delivery is performed. Sender remains accountable for the handoff until acceptance.

read_handoff exposes explicitly shared snapshot terms to current sender/receiver only. Source/next links require independent detail access. History follows exact revision recipient scope. Files expose no parent body, source URL/access notes, Storage path or financial link. Package revision UUID is a narrow download context accepted by the existing authorize_asset_download/Edge streaming protocol: only exact finalized manifest items, current authorized recipient/sender and current proposed/accepted revision. It grants no raw asset/manifests/origin/parent scope. Superseded, withdrawn, expired/revoked or reassigned contexts fail closed. P12's attachment/hash/no-store and second authorization checks remain; its existing origin/linked-record path is preserved.

src/features/handoffs/api.ts exposes typed submit/respond/accept/read through real SDK RPCs; gateway.handoffs is wired. Caller keys/versions are explicit, errors sanitized, malformed receipts rejected, no hidden retries or fake success. P17's local SQL/adapter/byte proof remains in test:handoffs and verify-p17.cjs. Provider/JWT/true-concurrency/institutional authority/privacy/human gates remain in STATE/P17.

## P18 interface

Migration026 adds current-party names/action flags and independently scoped immutable revision metadata to read_handoff; the original P17 read remains private. Historical revisions follow the same exact-receiver/current-sender history rule as P17. Current package file contexts still authorize only proposed/accepted current revision bytes; historical/withdrawn metadata is not file access.

list_handoffs(term, incoming/outgoing/work, optional work ID, page) applies current core/package permission before totals and20-row pages. A work filter additionally requires independent current detail access to that exact same-term work. Source/next links retain their own P17 detail checks. A permitted next task can expose only neutral awaitingAcceptance when its package is not shared; no hidden package identity/title/state/count follows from that flag.

handoff_submission_options(source task, optional prior handoff) requires the current active Done-source owner/edit authority. It returns up to20 authorized source-origin finalized manifests with sanitized snapshot files and50 eligible existing successor/head choices. Successors require independent detail access, actual assigned recipient/unit, To do and live required finish-to-start edge, excluding another package's canonical next task. Package-only heads must also be visible through the existing directory function; no new directory grant. Resubmission choices require current sender scope; canSubmit reflects eligible state while an exact unresolved retry can recover its earlier receipt. These reads do not assign/create tasks or change P17 mutation rules.

Working together links incoming/outgoing handoffs; task details discover their permitted packages and offer submission from a completed owned source. /working-together/handoffs/:UUID is a safe core-only deep link. Package pages show exact output/criteria/files/hashes, parties, proposed Manila date, who owes the next action, explicit acceptance state, scoped source/next links, revision history and immutable receiver/time/notes receipt. Download streams pass the revision UUID through P12 and verify actual blob size/hash before attachment download; no inline source or file URL is exposed.

Receiver actions are accept exact revision, request changes and decline; sender action is withdraw and, when eligible, revised immutable submission. Acceptance requires an explicit current-revision checkbox and notes. Current server flags guide controls; P17 endpoints independently authorize every call. Stale/failed commands keep entered values, and refresh resets the revision confirmation. Unknown results freeze related controls and retry the exact original key/version/payload. Identity-bound React memory retains only explicit form inputs and pending requests across routine auth remounts; fresh read/options authorization precedes restoration, and scope/identity/term loss clears them. No persistent browser storage or full-reload durability claim. No local UI state can activate next work or fabricate a receipt.

Overview reads canonical current state, not outbox deliveries. One visible proposed/revision handoff replaces its pending next-task row. Receiver-proposed work is actionable; sender proposals/receiver feedback waits use the correct named party; sender changes/decline revisions are actionable. Accepted/cancelled handoff actions disappear; acceptance exposes the existing assigned task once. A hidden nonaccepted package supplies only neutral task waiting text. Both committee package views link the same accepted next-task UUID under independent detail access. Original ownership/deadlines and FIN/MCD/deliverable acceptance are preserved.
