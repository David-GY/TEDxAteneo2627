# Committee timeline contract (P16A)

The independent local implementation is delivered. Provider/authority/privacy and human acceptance remain blocked. Fictional records appear only in the isolated development preview, with an explicit synthetic banner; a disconnected production app has no fixture fallback.

Migration023 adds nullable `work_items.planned_start_on`, without a default or backfill. It is a Manila calendar date, supported from0001-01-01 through9999-12-31. A validated table CHECK rejects starts after `due_on` or the Asia/Manila calendar day of `due_at` in every writing command. Null starts and starts without an end remain valid. The existing pure helpers define inclusive/equal-day ranges, end-only deadline markers and incomplete unscheduled records.

`update_work_schedule(work ID, planned start or null, expected version, request UUID)` changes only the start. Current active core membership, active term, unarchived record and existing edit authority are required. Tasks additionally require their existing date-manager authority: configured scoped manager or self-created current owner; assignee progress alone is insufficient. Task states are To do/In progress/Blocked; deliverables use the existing Proposed/Draft/In progress authoring states. Accepted contributions fail closed because P14's negotiated terms do not yet carry a planned-start field; this helper cannot amend any agreed date. Existing deadline/revision flows remain authoritative. This is a deliberate conservative limitation pending an approved agreement start-term extension, not a new agreement flow.

The command uses P16's READ COMMITTED term graph lock before request/row locks, rechecks authority after locking and before receipt replay, checks expected version, and records one actual changed row/version, redacted field-name audit, receipt and outbox event. An identical start is rejected as a no-op. Exact caller/payload retries return the original receipt under current authority; changed-payload keys conflict. Original deadlines, workflow, criteria and FIN/MCD/acceptance fields are untouched. No raw client write grant was added.

Migration024 adds `read_committee_timeline(term ID, filters={}, page=1, page size=50)`. Guests, nonmembers, revoked/expired membership and non-active terms return null. Current detail authorization is materialized before subtype/unit joins, options, filtering, totals and pagination. This intentionally excludes ordinary-summary-only work from the new projection. Existing summary pages retain their established contract.

Each canonical deliverable/task/contribution appears once. The primary committee is receiving committee for a contribution, assigned/lead committee for a task, and lead committee for a deliverable. Actual related units are participation badges, not grants. Phase is the deliverable's own phase; tasks have null phase, with no inherited private parent metadata. Status is the real workflow state, not a percentage or approval. Blocking includes the permitted neutral task dependency/pending handoff readiness signal; hidden predecessors never expose IDs, titles or counts.

Accepted filters: `units` (up to20 UUIDs, OR within selection), `owner` UUID, `phase`, `type` (`task`, `deliverable`, `contribution`), boolean `blocked`/`overdue`, date-only `from`/`to`, boolean `includeUnscheduled` (default true). Categories combine with AND; false blocked/overdue means no such restriction. Invalid keys/types/UUIDs/dates and reversed windows fail. Dated work intersects the inclusive window. Start-only/no-end work can remain independently included. Empty unit selection means all permitted units.

The result contains items, total, page, pageSize, permitted owner/unit/phase options and required/informational P16 dependencies whose two endpoints are both loaded. Pages are1–10000; page size caps at100, with deterministic end-date/null-last/work-ID ordering. Options derive only from authorized rows before selected filters. Original deadlines and real detail routes are included only for those authorized records. No parent, source-manifest or finance metadata is added. This is always a partial graph, not proof of complete organizational coverage.

Migration025 adds `read_work_schedule(work ID)`: a narrow independent current core/detail read of dates/version and current scheduling availability. Guests, hidden records and inactive terms return null. Progress-only assignees and accepted contributions receive no date-edit authority. No record title/body, parent, file or finance access is added.

`src/features/timeline/api.ts` validates canonical IDs/routes, real statuses, strict dates, unique work identity, bounded pages and both-loaded dependency endpoints. The actual SDK uses the existing RPC commands; malformed receipts and uncertain replies never report success.

The route is `/working-together/timeline`, linked from Working together and Core deliverables. Week/month, previous/next/today, Manila today/April17,2027, committee/owner/phase/type/blocked/overdue and unscheduled controls use validated URL parameters. Safe sign-in return paths preserve only these fields. Overdue-only deliberately includes earlier windows through Manila today, so older incomplete work remains in the chronological list even outside the drawn chart. Timeline query-only navigation uses the RPC's independent authorization without resetting controls; explicit focus/expiry/visibility checks still revalidate workspace identity. Refresh/focus/visibility and a visible30-second interval clear old rows/options before fetching; failures/denial retain no old result. Pagination and chart/list choice remain in the URL.

The read-only native chart clips inclusive bars to its calendar window, draws end-only diamonds without a duration, and marks today/event when in view. Primary committee labels and full participating-unit names come from permitted canonical records. Solid required and dashed informational/optional links use only loaded drawn endpoints. The chronological alternative exposes all loaded dates, owners, statuses, original targets and permitted link descriptions, including unscheduled work. Scrolling stays inside the chart; controls/focus and320px/640CSSpx reflow use the incumbent Karla system. No drag/resize/date shifting, percentage-complete or approval badges.

Planned-start forms sit beside the existing task/deliverable editors. Creation continues through the established command; set optional start after the canonical record exists. A start save changes only that date, preserves other current unsaved fields, and tells the user to reload the record when ready before saving from its older version. Explicit schedule refresh keeps the entered date. An uncertain request freezes schedule/related controls and retries its exact original payload/version/key. A small identity-bound memory store retains only the date/base version/retry metadata across routine authentication remounts. Fresh record access is required before restoration; denied scope, sign-out or identity/term change clears it. It stores no notes/files or browser local/session storage; full browser reload is not durable draft storage. Other existing record-editor authentication behavior is retained.
