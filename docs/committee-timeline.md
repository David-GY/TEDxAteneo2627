# Committee timeline contract (P16A partial)

The calendar helpers and server foundation are implemented. The timeline route, client API adapter, chart/list, schedule forms and browser acceptance are still pending. No production or fictional chart is presented as a completed feature.

Migration023 adds nullable `work_items.planned_start_on`, without a default or backfill. It is a Manila calendar date, supported from0001-01-01 through9999-12-31. A validated table CHECK rejects starts after `due_on` or the Asia/Manila calendar day of `due_at` in every writing command. Null starts and starts without an end remain valid. The existing pure helpers define inclusive/equal-day ranges, end-only deadline markers and incomplete unscheduled records.

`update_work_schedule(work ID, planned start or null, expected version, request UUID)` changes only the start. Current active core membership, active term, unarchived record and existing edit authority are required. Tasks additionally require their existing date-manager authority: configured scoped manager or self-created current owner; assignee progress alone is insufficient. Task states are To do/In progress/Blocked; deliverables use the existing Proposed/Draft/In progress authoring states. Accepted contributions fail closed because P14's negotiated terms do not yet carry a planned-start field; this helper cannot amend any agreed date. Existing deadline/revision flows remain authoritative. This is a deliberate conservative limitation pending form integration, not a new agreement flow.

The command uses P16's READ COMMITTED term graph lock before request/row locks, rechecks authority after locking and before receipt replay, checks expected version, and records one actual changed row/version, redacted field-name audit, receipt and outbox event. An identical start is rejected as a no-op. Exact caller/payload retries return the original receipt under current authority; changed-payload keys conflict. Original deadlines, workflow, criteria and FIN/MCD/acceptance fields are untouched. No raw client write grant was added.

Migration024 adds `read_committee_timeline(term ID, filters={}, page=1, page size=50)`. Guests, nonmembers, revoked/expired membership and non-active terms return null. Current detail authorization is materialized before subtype/unit joins, options, filtering, totals and pagination. This intentionally excludes ordinary-summary-only work from the new projection. Existing summary pages retain their established contract.

Each canonical deliverable/task/contribution appears once. The primary committee is receiving committee for a contribution, assigned/lead committee for a task, and lead committee for a deliverable. Actual related units are participation badges, not grants. Phase is the deliverable's own phase; tasks have null phase, with no inherited private parent metadata. Status is the real workflow state, not a percentage or approval. Blocking includes the permitted neutral task dependency/pending handoff readiness signal; hidden predecessors never expose IDs, titles or counts.

Accepted filters: `units` (up to20 UUIDs, OR within selection), `owner` UUID, `phase`, `type` (`task`, `deliverable`, `contribution`), boolean `blocked`/`overdue`, date-only `from`/`to`, boolean `includeUnscheduled` (default true). Categories combine with AND; false blocked/overdue means no such restriction. Invalid keys/types/UUIDs/dates and reversed windows fail. Dated work intersects the inclusive window. Start-only/no-end work can remain independently included. Empty unit selection means all permitted units.

The result contains items, total, page, pageSize, permitted owner/unit/phase options and required/informational P16 dependencies whose two endpoints are both loaded. Pages are1–10000; page size caps at100, with deterministic end-date/null-last/work-ID ordering. Options derive only from authorized rows before selected filters. Original deadlines and real detail routes are included only for those authorized records. No parent, source-manifest or finance metadata is added. This is always a partial graph, not proof of complete organizational coverage.

Actual evidence: `pnpm test:committee-timeline`, SQL assertions and `docs/build/evidence/P16A-schedule.json`. These use isolated PGlite and fictional subjects. Named A1/A2 server cases and the five calendar helper tests pass; client integration/revalidation/A3 and all inherited real provider/session/privacy/authority/human gates remain unverified. See the P16A checkpoint for exact commands, failures/corrections, usage and continuation.
